# tksnslogicservice 项目分析文档
## 一、项目概述
### 1. 项目基础信息
- **项目名称**：tksnslogicservice
- **开发语言**：C++
- **运行环境**：Linux
- **构建工具**：CMake（最低版本要求 2.6）
- **核心定位**：基于 SNS（社交网络服务）的逻辑服务端，提供关系管理、礼物系统、数据存储与交互等核心功能，作为社交相关业务的后端支撑服务。

### 2. 项目核心依赖
项目依赖多个内部封装的工具库和第三方库，确保功能实现的高效性和稳定性：
| 依赖类型 | 具体依赖 | 用途 |
|----------|----------|------|
| 内部工具库 | tkmessage、tkcommon、tkthreadpool、tkasynlog | 基础通信、通用工具、线程池管理、异步日志 |
| 数据存储库 | tkmysqlpool、tkredispool、tkmongopool | MySQL 连接池、Redis 连接池、MongoDB 连接池 |
| 网络库 | tksocketlibrary | 网络通信、Socket 连接管理 |
| 第三方库 | mysqlclient、ssl、crypto、pthread、mongoc-static-1.0、bson-static-1.0 | 数据库驱动、加密、线程、MongoDB 客户端 |
| 解析库 | rapidjson、rapidxml | JSON/XML 数据解析 |

## 二、项目架构设计
### 1. 整体架构分层
项目采用模块化分层设计，各组件职责清晰，耦合度低，便于维护和扩展：
```
┌─────────────────────────────────────────────────────────┐
│ 网络层（SockServer + MessageHandler）                    │
│ - 负责接收客户端/其他服务的请求，返回响应                │
│ - 核心类：CTKSNSLogicServiceHandler、SockServer          │
├─────────────────────────────────────────────────────────┤
│ 业务逻辑层（核心服务 + 模块管理）                        │
│ - 关系管理模块：节点创建、成员增删、属性维护             │
│ - 礼物系统模块：赠送、领取、过期返还                    │
│ - 核心类：CTKSNSLogicService、CTKSNSNodeBase、CTKSNSGiftMgr │
├─────────────────────────────────────────────────────────┤
│ 数据访问层（存储管理）                                  │
│ - 缓存层：Redis（关系ID生成、礼物信息缓存、领取计数）    │
│ - 持久化层：MongoDB（关系数据存储）、MySQL（预留扩展）  │
│ - 核心类：CTKSNSRedisMgr、CTKSNSMongoMgr、CTKSNSMySQLMgr │
├─────────────────────────────────────────────────────────┤
│ 基础支撑层（工具 + 协议）                              │
│ - 工具类：JSON解析、日志、线程池、配置读取              │
│ - 协议定义：内部服务通信协议、消息格式定义              │
└─────────────────────────────────────────────────────────┘
```

### 2. 核心模块关系
- **核心服务入口**：CTKSNSLogicService 是项目核心，管理所有模块的初始化、生命周期和业务调度。
- **模块依赖**：业务逻辑层依赖数据访问层实现数据存储与查询，依赖基础支撑层提供工具和协议支持；网络层依赖业务逻辑层处理具体请求。
- **单例设计**：通过全局指针 `g_ptkSNSLogicService` 提供核心服务的全局访问，确保模块间交互的一致性。

## 三、核心功能分析
### 1. 关系管理（核心业务之一）
基于“节点（Node）”概念管理各类社交关系，支持多种关系类型和业务操作，是 SNS 服务的基础。

#### 1.1 关系类型定义（ENUM_SNS_NODE_TYPE_DEF）
支持多种社交关系节点，覆盖个人、组织、临时互动等场景：
- 私人关系：好友、黑名单、关注、被关注、陌生人、最近联系人
- 组织关系：战队、家族、粉丝团、周期性团队
- 临时关系：临时讨论组、队伍临时讨论组、自建桌临时讨论组、最近同玩

#### 1.2 核心业务操作（ENUM_SNS_BIZ_TYPE_DEF）
| 操作类型 | 功能描述 | 实现逻辑 |
|----------|----------|----------|
| 创建（CREATE） | 新建关系节点（如战队、临时讨论组） | 生成唯一节点ID，解析创建参数，初始化节点属性（名称、创建时间、加入类型等），存储到MongoDB |
| 解散（DELETE） | 删除关系节点 | 从MongoDB删除节点数据，清理相关缓存 |
| 添加成员（ADD_MEM） | 向关系节点添加成员 | 解析成员信息（ID、昵称），更新节点成员列表，同步到存储 |
| 删除成员（DEL_MEM） | 从关系节点移除成员 | 验证操作者权限（管理员），移除成员，若成员数为1则自动解散节点 |
| 查询（QUERY） | 查询节点信息或成员属性 | 从存储中读取节点属性、成员列表，返回格式化结果 |
| 修改（MODIFY） | 修改节点或成员属性 | 支持更新节点名称、公告、成员职务等属性 |

#### 1.3 关键类与逻辑
- **CTKSNSNodeBase**：关系节点基类，定义通用接口（属性设置、成员管理、业务处理），采用虚函数实现多态。
- **CTKSNSNodeTeamTempGroup**：临时讨论组子类，继承自 NodeBase，实现临时讨论组的专属创建、成员管理逻辑。
- **CTKSNSNodeMgr**：节点管理器，根据节点类型创建对应的节点实例，统一调度业务操作。

### 2. 礼物系统（核心业务之二）
提供完整的礼物赠送、领取、过期返还流程，支持多种礼物类型和规则控制，依赖 Redis 实现高效缓存和计数。

#### 2.1 礼物核心定义
- **礼物类型（ENUM_SNS_GIFT_TYPE_DEF）**：500PK团赛券、2000PK团赛券、家族赛复活卡。
- **操作类型（ENUM_SNS_PROCESSGIFT_REQ_TYPE_DEF）**：赠送（SEND）、领取（RECV）、返还（RETURN）。
- **错误码（ENUM_SNS_PROCESSGIFT_ERR_CODE_DEF）**：参数错误、礼物不足、已领取、过期、不在领取名单、领取上限等。

#### 2.2 核心流程
##### （1）礼物赠送（SendGift）
1. 解析请求参数（用户ID、礼物类型、接收者列表），验证参数合法性。
2. 根据礼物类型获取对应的 ECA 方案ID，调用 ECA 服务扣除用户对应的礼物资源。
3. 生成唯一礼物 UUID，设置过期时间（默认 86400 秒=24小时）。
4. 将礼物信息（请求JSON、过期时间、UUID）存储到 Redis（Hash 结构 `GiftInfo:UUID`），并添加到礼物列表（Sorted Set `GiftList`）。

##### （2）礼物领取（RecvGift）
1. 解析请求参数（用户ID、礼物UUID），从 Redis 获取礼物信息。
2. 验证礼物状态：未被领取、未过期、领取者在接收者列表中（若指定）。
3. 验证用户领取次数：每月最多领取15个（通过 Redis 键 `GiftRecvCount:UserID:YYYYMM` 计数）。
4. 原子设置礼物领取标识（避免并发领取），调用 ECA 服务向领取者发放礼物资源。
5. 递增用户月度领取计数，更新礼物状态。

##### （3）过期返还（OnAsyncExpireReturn）
1. 启动异步定时任务（每60秒执行一次），从 Redis 读取所有未过期的礼物列表。
2. 遍历礼物，筛选已过期且未被领取的礼物。
3. 调用 ECA 服务将礼物资源返还给赠送者，从 Redis 中删除礼物信息和列表记录。

#### 2.3 关键类与逻辑
- **CTKSNSGiftMgr**：礼物系统核心管理器，负责初始化配置、调度赠送/领取/返还流程、异步任务管理。
- **CTKSNSRedisMgr**：提供礼物相关的 Redis 操作（存储、查询、计数、过期处理），确保高并发场景下的性能和数据一致性。
- **ECA 交互**：通过 `ExcuteECA` 方法与 ECABrokerService 通信，实现礼物资源的扣除与发放，依赖 Socket 连接池管理通信连接。

### 3. 数据存储设计
#### 3.1 Redis 用途（核心缓存）
| Key 格式 | 类型 | 用途 | 过期策略 |
|----------|------|------|----------|
| GiftInfo:UUID | Hash | 存储礼物详情（请求JSON、过期时间、领取标识、返还标识） | 30天（24*3600*30秒） |
| GiftList | Sorted Set | 存储礼物UUID，分值为过期时间戳 | 无（通过定时任务清理过期数据） |
| GiftRecvCount:UserID:YYYYMM | String | 记录用户月度领取礼物次数 | 60天（24*3600*60秒） |
| NodeMaxID:NodeType | String | 生成关系节点唯一ID（通过 INCR 原子递增） | 永久 |

#### 3.2 MongoDB 用途（持久化存储）
- 存储关系节点数据，集合名称格式为 `NodeKeyPre_NodeType`（如 `sns_node_18` 对应队伍临时讨论组）。
- 文档结构包含节点属性（node_prop）和成员属性（mem_prop），与 `TKSNSPropBaseDataDef` 结构对应。
- 支持节点数据的插入、删除、更新、查询操作（通过 CTKSNSMongoMgr 封装）。

#### 3.3 MySQL 用途（预留扩展）
- 初始化了 MySQL 连接池（分为字典库和日志库），但当前代码未实现具体业务操作，预留用于需要事务支持或复杂查询的场景（如用户关系日志、统计数据）。

### 4. 网络通信与协议
#### 4.1 通信模式
- 基于 Socket 实现 C/S 架构，支持与 SnsPivotService、ECABrokerService、SnsClient 等服务/客户端通信。
- 采用连接池管理 Socket 连接（CDisSockConnPool），提高通信效率，支持高并发请求。

#### 4.2 核心协议定义
- **内部服务协议**：定义于 `TKSNSBroker2SNSLogicProtocol.h`，如礼物处理请求 `TKID_SNSBROKER2SNSLOGIC_PROCESSGIFT`，消息格式包含头部（TKHEADER）、后缀数据（JSON格式）。
- **ECA 服务协议**：定义于 `TKECABrokerS2SnsPivotSProtocol.h`，如带参数的 ECA 操作请求 `TKID_ECABROKERS2SNSPIVOTS_ASKFORPARAMECA`，支持资源扣除/发放的参数传递。
- **协议基础**：所有协议基于 `TKProtocol.h` 定义的头部（TKHEADER）和后缀（TKSUFFIXIDX）结构，统一消息格式。

### 5. 配置与初始化
#### 5.1 配置读取
- 从 INI 配置文件读取核心参数，如：
  - 礼物配置（GiftConfig）：各类礼物对应的 ECA 方案ID、用户月度领取上限、礼物过期时间。
  - 数据库配置（MongoDB、MySQLDic、MySQLLog、SNSRedis）：连接地址、端口、用户名、密码、连接池大小。
  - 异步任务配置（AsynMsgFunctor）：礼物处理、关系操作的线程池大小。

#### 5.2 初始化流程
1. 启动服务主程序（TKSNSLogicServiceMain.cpp），初始化消息处理器和核心服务。
2. 核心服务初始化（CTKSNSLogicService::Init）：
   - 初始化 Socket 连接池、日志、消息统计。
   - 初始化 Redis、MongoDB、MySQL 连接池（MongoDB 和 MySQL 可选初始化）。
   - 初始化礼物管理器（CTKSNSGiftMgr），加载礼物配置，启动异步过期返还任务。
3. 启动服务线程，监听网络请求，处理定时任务（如过期返还、状态上报）。

## 四、业务场景与应用
### 1. 目标业务场景
该项目是社交类应用（如游戏社交、社区平台）的后端核心服务，主要支撑以下场景：
- **游戏社交场景**：玩家创建战队、家族等组织关系，添加/移除成员，通过赠送礼物（如比赛券、复活卡）增强互动，提升组织凝聚力。
- **社区互动场景**：用户关注、添加好友，通过礼物系统表达心意，系统通过领取上限、过期返还规则保障礼物价值和用户体验。
- **临时互动场景**：用户参与临时讨论组、最近同玩等临时关系，通过礼物激励用户积极参与互动。

### 2. 核心价值
- **关系管理标准化**：支持多种关系类型和业务操作，提供统一的接口和存储方案，降低社交功能的开发复杂度。
- **高并发支持**：基于 Redis 缓存和线程池设计，支持高并发的礼物赠送/领取和关系操作，满足大规模用户场景。
- **可扩展性强**：采用模块化设计，新增关系类型或礼物类型时，只需扩展对应的子类和配置，无需修改核心逻辑。
- **数据一致性保障**：通过 Redis 原子操作、ECA 服务事务支持、定时任务清理，确保礼物流程和关系数据的一致性。

## 五、构建与部署
### 1. 构建配置（CMakeLists.txt）
- **编译选项**：支持 32 位编译（-m32）、C++11 标准、Wall 警告级别，根据构建类型（Debug/Release/RelWithDebInfo）设置优化参数（-g 调试、-O2 优化）。
- **输出目录**：可执行文件输出到项目根目录的 `bin` 文件夹。
- **构建产物**：
  - Debug 模式：生成带 `_d` 后缀的可执行文件（如 `tksnslogicservice_d`），链接调试版本库（如 tkmessage.debug）。
  - Release/RelWithDebInfo 模式：生成正式可执行文件（如 `tksnslogicservice`），链接正式版本库。

### 2. 部署要求
- 运行环境：Linux 系统（支持 32 位编译，如 CentOS 7、Ubuntu 16.04）。
- 依赖安装：需提前安装 MySQL、Redis、MongoDB 服务，以及对应的开发库（如 libmysqlclient-dev、libmongoc-dev、libbson-dev）。
- 配置文件：需提供 INI 配置文件，包含数据库连接信息、礼物配置、线程池大小等参数。

## 六、总结
tksnslogicservice 是一个功能完善、架构清晰的 SNS 逻辑服务端项目，核心聚焦于**社交关系管理**和**礼物互动系统**，通过模块化设计、高效缓存、标准化协议，支撑高并发、多场景的社交类应用需求。

### 核心优势
1. 业务覆盖全面：支持多种社交关系类型和完整的礼物生命周期管理，满足社交互动的核心需求。
2. 性能高效：基于 Redis 缓存和线程池设计，确保高并发场景下的响应速度和稳定性。
3. 可扩展性强：采用面向对象的多态设计，新增业务模块或扩展功能时无需修改核心代码。
4. 数据可靠：通过多存储方案（缓存+持久化）和一致性保障机制，确保数据安全和业务正确性。

### 潜在扩展方向
1. 新增关系类型：如兴趣小组、社区板块等，扩展社交场景覆盖。
2. 礼物功能增强：支持礼物赠送特效、赠送记录查询、礼物排行榜等功能。
3. 数据分析：利用 MySQL 存储用户互动数据，提供社交行为分析、礼物消费统计等增值服务。
4. 分布式扩展：支持多节点部署，通过负载均衡提升服务的可用性和并发处理能力。
